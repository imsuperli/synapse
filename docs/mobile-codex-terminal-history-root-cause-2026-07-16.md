# 手机端 Codex 终端历史不完整、缩放后无法滚动：根因与修复记录

## 问题记录

复现环境：手机通过公网 relay 连接 PC 端 Synapse，PC 终端中的 Codex 已运行较长时间。

观察到的现象：

- 手机首次进入终端只显示十几行，向历史方向下拉没有反应。
- 缩小字体后偶尔可以滚动更多内容，但终端内容只占屏幕上方；重新放大后又无法滚动。
- 强制关闭并重启手机端后，显示的内容会变化，有时只剩一行 `Working ...`。
- 即使某个缩放比例下能够滚动，手机端显示的历史仍不完整。
- 此问题此前修改过多次，包括历史分页、二进制快照、前后台恢复和 Codex `CSI S` scrollback 保留，但没有彻底解决。

## 第一轮排查结论

这不是单一问题，而是三个移动端缺陷叠加；此前的 `CSI S` 修复解决了第四个独立问题，但没有覆盖这三个缺陷。

### 1. 放大后的单指手势被画布平移无条件截获

远程终端使用 `textScaleMode="viewport-zoom"`。字体比例大于 1 时，`terminal-webview-html.ts` 会优先把单指拖动解释为缩放画布平移。

旧逻辑的问题是：即使 `panX/panY` 已经到达边界，`clampPan()` 后坐标完全没有变化，事件仍然直接 `return`。因此：

- xterm normal buffer 收不到垂直滚动；
- 到达已加载历史顶部时不会发出 `history-top`；
- React Native 层无法激活或继续请求更早历史。

这直接解释了“默认比例不能滚动，但换一个缩放比例又偶尔能滚”的现象。缩放改变了画布是否溢出及平移边界，进而改变手势被哪一层消费。

### 2. 第一轮错误地把显示高度问题归因于手机行数不足

第一轮修复认为远程终端保留 PC 列数后，还应该根据手机高度增加 xterm 行数：

```text
fitScale = viewportWidth / terminalWidth
rows = viewportHeight / (cellHeight * fitScale)
```

以 360 x 640、120 列、8 x 15 单元格为例，该计算会把桌面行数替换成约 113 行。这个思路只考虑了几何高度，却忽略了终端回放语义：PTY 原始输出中的光标定位、清屏和滚动区域都基于 PC 当时的完整行列网格。只修改手机 xterm 的行数会改变回放结果，可能把本来有效的 TUI 快照清空。

因此，“增加手机行数”不是正确修复。手机必须完整保留 PC 的列数和行数，屏幕适配只能使用统一 CSS 比例和平移。

### 3. 后台预取的历史依赖到顶手势进入 xterm

首次二进制订阅为加快首屏，只返回最近 128 KiB。手机随后会按 192 KiB 分页、最多约 768 KiB 地后台预取更早历史。

旧实现只把这些页保存在 React Native 内存中。只有 WebView 发出 `history-top` 后，页面才会把预取页 prepend 到历史状态并重新初始化 xterm。

由于根因 1 阻止了 `history-top`，第一轮排查时的结果是：

- 更早历史已经通过 relay 下载到手机；
- 但它没有进入 xterm，用户始终只能看到首屏最近 128 KiB 的回放结果；
- 重启后首屏截取位置、Codex 当前重绘状态及快照时序不同，所以看到的几行也会变化。

这个交互主要由提交 `06c5a82` 引入：首屏变快了，但预取数据依赖一个后来被缩放手势阻断的激活条件。

### 4. 此前修复的 Codex `CSI S` 回放问题仍然成立

提交 `5217e9e` 在手机 xterm 中安装了与 PC 端等价的 `CSI S` scrollback preservation handler，避免 Codex 顶部滚动区域回放时删除 normal scrollback。

该修复是必要的，但只保证“已送入 xterm 的原始 PTY 字节不会在回放时被 `CSI S` 删除”。它不能解决：

- 预取页根本没有送入 xterm；
- 放大后手势无法到达 xterm；
- xterm 行数计算使终端表面只占视口上方。

## PC 端是否会丢失历史

PC 主进程保留的可恢复 PTY 历史是有边界的内存环形缓存：

- 最多 250,000 个输出块；
- 最多 20,000,000 个字符；
- 超出任一上限时淘汰最旧输出，并更新 `evictedBeforeSeq`；
- PC 应用完全退出后不会跨进程持久化；
- PTY 进程退出时，`ProcessManager.finalizeProcessExit()` 当前会立即删除对应 pane 的原始历史和 screen snapshot。

因此 PC 端确实存在“超过缓存边界、应用退出或 PTY 退出后不可恢复”的历史丢失边界。此次用户复现中的主要问题发生在终端仍可订阅且 PC 仍返回历史时，根因是移动端没有正确展示这些数据；但移动端现在会明确区分：

- 自然到达 PC 当前保留历史的开头；
- 更早输出已经被 PC 缓存淘汰。

## relay 排查结论

relay 不是此次静默截断的直接原因：

- 单个历史页约 192 KiB，低于 relay/host 的 1 MiB 消息限制；
- WebSocket 保证同一连接内有序可靠传输；
- relay 的限流或背压路径会关闭连接并触发重连，而不是静默只保留几行；
- 手机诊断会记录连接状态、重连阶段及每个历史页实际返回的序号和字符数，可继续验证公网链路。

## `a9bbd24` 引入的严重回归

第一轮修复提交 `a9bbd24`（`test-android-20260716-144409`）采用了“增加手机行数”和“首批历史自动激活”。用户提供的新诊断日志确认这两个改动共同造成了更严重的回归。

日志中的实际几何数据为：

```text
PC replay grid: 228 x 70
phone viewport: 369 x 600
cell: 7.547 x 15.094
mobile grid after refit: 228 x 185
fitScale: 0.21444
```

具体表现与原因：

- 首屏先按正确的 `228×70` 回放，随后 `measure-fit` 返回 185 行并再次初始化为 `228×185`，因此进入终端时会先显示几行，再闪烁或清空。
- 宽度缩放 `369 / (228 * 7.547) = 0.21444` 同时作用于高度，15 px 字形最终只有约 3.2 px 高，造成文字压窄、变形。
- `228×185` 表面按 `0.21444` 缩放后高度仍只有约 598 px；实际回放和容器切换时还会出现明显空白与不稳定布局。
- 首批约 1 MiB 历史自动激活会立即重建 xterm；之后每次 `history-top` 又用不断增长的完整历史重建，日志中的累计回放从 1.1 MiB 增长到 9.7 MiB。
- `history-top` 在 `touchmove`、手指尚未抬起时触发，甚至 `0.17 px`、`1.18 px` 的微小移动也能启动历史加载；新 surface 替换正在触摸的旧 surface，直接造成单次下拉闪烁。

日志同时证明 relay 和 PC 历史返回正常：所有分页均为 `gap=false`，序号连续，且 PC 明确给出 `evictedBeforeSeq=1100170`。本次回归发生在手机端布局、手势和重放策略。

## 最终采用的修复方案

### 手势交接

- 依据手势主轴决定横向或纵向画布平移，避免轻微横向抖动阻断垂直滚动。
- 只有 `clampPan()` 后 `panX/panY` 确实变化时才消费事件。
- 位于画布边界时，同一个手势继续进入 xterm normal scrollback；在已加载顶部继续触发 `history-top`。
- 保留横向放大画布的正常平移能力。
- 到顶后必须累计至少 24 px 的明确下拉，微小触碰不会加载历史。
- 手指按下期间只记录待处理请求，直到 `touchend`/`touchcancel` 才最多发送一次 `history-top`。
- 惯性滚动到顶只停止动画，不会在手指抬起后再触发一次历史重建。

### 固定 PC 回放网格与等比铺满

远程移动端 xterm 始终使用 PC 快照提供的完整网格：

```text
mobileCols = desktopCols
mobileRows = desktopRows
```

手机只对完整网格使用统一比例：

```text
widthScale = viewportWidth / terminalWidth
heightScale = viewportHeight / terminalHeight
fitScale = max(widthScale, heightScale)
```

这样不会改变字符宽高比，也不会改变 ANSI 回放坐标。终端至少铺满手机视口；宽桌面网格超出的部分允许横向平移。日志中的 `228×70` 示例缩放约为 `600 / (70 * 15.094) = 0.568`，而不是导致字形压缩的 `0.214`。

### 历史按需激活

- 首屏快照完成后继续后台预取历史。
- 首批预取不再自动 prepend 或重建 xterm，避免启动后立即闪烁。
- 只有用户到达已加载顶部并完成一次有效下拉后，才激活当前缓存批次。
- 重建期间旧 surface 保持可见；新 surface 完成完整回放和等比缩放后才原子替换并发送 `ready`。
- 激活后立即在后台补充下一批缓存。

### PC 淘汰边界传播

- `gap` 和 `evictedBeforeSeq` 现在贯穿 snapshot、prefetch cache、take 和 prepend 全流程。
- 到达边界时分别显示“已到达最早缓存输出”或“更早输出已被电脑端内存缓存淘汰”。

### 历史边界提示

- “已达到电脑缓存的最早输出”等边界提示显示 3 秒后自动消失。
- 新的历史加载、终端重连、清屏或切换会话会立即清除旧提示。

## 移动端诊断日志

终端页原生标题栏新增诊断按钮。点击后可查看日志，并通过“复制日志”一次性复制全部诊断，不需要 Metro、ADB 或连接电脑。

日志特性：

- 最多保留最近 100 条；
- 已脱敏后持久化到移动端本地存储，App 重启后仍可读取上一轮复现记录；
- App 进入后台时立即刷新持久化数据；
- JSON Lines 格式，便于直接粘贴到 issue 或脚本分析；
- 不记录终端正文、键盘输入、剪贴板内容、token、密钥或完整敏感 URL。

记录范围：

- 网络：连接阶段、relay/direct 类型、重连及连接日志；
- PC 返回：请求游标、返回序号范围、块数、字符数、最新序号和 `evictedBeforeSeq`；
- 手机缓存：每批预取只记录一条汇总，包括页数、字节数、下一游标和手动激活结果；
- WebView：fit scale、字体比例、总缩放、`panX/panY`、行列、单元格尺寸、buffer type/length、`baseY/viewportY` 和手势路由。

## 回归验证标准

- 在 1.25、1.5、2 倍字体比例下，画布顶部的有效下拉在抬手前不触发、抬手后只触发一次 `history-top`。
- 小于 24 px 的触碰抖动和抬手后的惯性均不会触发历史加载。
- 实际可移动的横向放大画布仍由 viewport pan 消费。
- PC `228×70` 网格在 369 x 600 手机视口中仍为 `228×70`，统一比例约 0.568，高度铺满且宽度可平移。
- 首屏完成后的后台预取不会自动重建 xterm。
- `gap/evictedBeforeSeq` 经预取和激活后不丢失。
- 历史边界提示会在 3 秒后消失。
- 诊断日志最多 100 条、分页按批汇总、可复制、可跨 App 重启恢复，并自动脱敏。
- 原有 Codex `CSI S` scrollback、终端重连、增量同步和输入路由测试继续通过。

## 未改变的边界

- 本次没有把 PC 的 PTY 历史改成磁盘持久化，也没有改变 20,000,000 字符/250,000 块上限。
- 本次没有扩大 128 KiB 首屏快照；后台预取仍保留，但只在明确的到顶手势后激活。
- xterm 自身 scrollback 仍有容量上限，极长会话最终仍受移动端渲染缓存和 PC 原始历史缓存共同约束。
